> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「面试要考 Go 并发、但只背过 channel 金句」的人一条能亲手跑出红绿的赛道——
> 骨架是一个 Go 写的**任务分发 / 名额发放网关**，并发缺陷是故意埋进去的，判据就是 `go test -race`。

**卖点（三条以内）**

1. **`go test -race` 是教科书级的天然红绿判据**：有竞争就报，没竞争就过——判据不需要我们发明断言，探测器本身就是判据。更关键的是它是 **happens-before 动态分析**而不是「跑得快慢」的采样：两个 goroutine 之间缺一条同步边它就报，**不需要它们真的同时执行**，所以单核机器上一样红。这比 seckill 那条「100 线程抢 10 库存」的并发判据确定性更高。
2. **零基础设施**：没有 MySQL / Redis / compose，判据全在进程内跑完。学员机器门槛是所有候选 Track 里最低的一条，CI 也不用等 healthy。
3. **证明平台不只支持 Java**：Go 的构建与判据约定和 Java 完全不同（包路径当 `test_group`、`_test.go` 而不是 `src/test`、build tag 当环境体检、`-race` 是判据的一部分）。跑通它意味着平台的多语言契约真的成立——这正是开源社区贡献最需要看到的那一步。

## 1. 判据可行性论证（最重要的一节）

### 1.1 判据的组合公式

本 Track 每个 stage 的 canonical 判定都是**两条同时成立**：

```
canonical 绿  =  ① 竞争探测器（-race）全程没有任何 WARNING
              ∧  ② 本 stage 的确定性锚点（结构性断言，与探测器无关）
```

为什么必须是两条，而不是「`-race` 干净就算过」：

- 探测器**只观察执行到的访问**。测试覆盖不到的路径、没被真正跑到的分支，它一律不报——所以「`-race` 干净」单独不构成「没有竞争」的证明。
- 反过来，结构性锚点（比如「丢更新之后总数对不上」）**大多只在真并行时才显形**：单核机器上（`GOMAXPROCS=1`，容器只分到 1 核）两个访问可能永远不重叠，断言就假绿了。

两个失效模式恰好互补，所以规格里给每个 stage 都配了至少一条 ②（见 §1.3 的「确定性锚点」列），并且把它写成 canonical 测试里的一条真实用例。任一条红即红，两条都绿才绿——**「绿」是诚实的**这一点，就落在这个 ∧ 上。

### 1.2 为什么 race detector 是「确定性」判据（以及它的边界）

`go test -race` 背后是 ThreadSanitizer：影子内存 + 向量时钟。它判定的不是「两个访问是否在同一纳秒发生」，而是「这两个访问之间有没有 happens-before 关系」。这条性质带来三个直接后果，也是本 Track 判据的地基：

1. **不需要真并行。** 只要两个 goroutine 对同一内存位置做过访问、且它们之间没有同步边，就报竞争。所以单核、慢机器、CI 小容器上一样红。这与「丢更新」这种要靠真并行才显形的现象形成鲜明对照——**这正是它比业务断言更硬的地方**，也是本 Track 敢把并发做成 canonical 判据的原因。
2. **故障夹具的同步必须是「只往前、不往横」的。** 这是最容易写错的一处：夹具只提供一条「开始闸门」（main 关闭 channel 或 broadcast），它建立的是 **main → 每个 worker** 的边；收尾用 `WaitGroup`，建立的是 **worker → main** 的边。worker 与 worker 之间**没有任何边**——否则竞争会被夹具自己「同步掉」，测试变成永远绿。所有阶段的 `testkit` 都必须遵守这条纪律，写规格之外的实现时要拿它做 code review 的第一条。
3. **边界三条（诚实记账）：**
   - 只有**执行到**的访问才被观察。绕过它的办法是让竞争段有足够的迭代量（本 Track 统一用「开始闸门 + 8 个 goroutine × 2 万次」，量级由 `testkit.RaceLoop` 固定）。
   - 影子内存每个字只有 4 个槽位，理论上存在「被后来的访问驱逐而漏报」的构造。应对不是加大迭代量赌运气，而是**每个 stage 至少一条与 TSan 无关的锚点**（§1.5 的五类），再叠 `-count=3` 复跑。
   - 「逻辑竞态」（比如 `先查后写` 的 TOCTOU：两次访问各自都有锁、但复合操作不是原子的）不是数据竞争，探测器**不报**。所以 stage 01 的去重缺陷不能只靠 `-race`，必须另配计数守恒断言——这就是 §1.1 那个 ∧ 的由来。

### 1.3 逐 stage 的红→绿形状

| stage | 骨架初始哪个用例失败 | 为什么失败（业务缺陷） | 确定性锚点（不进依赖探测器） | 参考解绿成什么样 | 只能可观测 |
|---|---|---|---|---|---|
| 01 `data-race` | `TestConcurrentGrant` / `TestCounterUnderConcurrency` | 注册表 map 无同步；计数器 `n++` 无同步；`Grant` 是「先查后写」的非原子复合操作 | 并发写 map 触发运行时自带的 `concurrent map writes`（`throw`，与 `-race` 无关）；计数守恒断言 | 并发发放后「被接受的数量 = 计数器 = 每个用户列表长度」，且探测器无报告 | TSan 的漏报边界本身不可断言 |
| 02 `channel-semantics` | `TestStreamClosesOutputExactlyOnce` / `TestStreamCancellable` / `TestNilErrorChannelDisabled` / `TestUnbufferedBackpressure` | `range in` 结束后没 `close(out)`；`select` 里没有 `ctx.Done()` 分支；nil 通道被直接塞进 `select`；用 `len(ch)==cap(ch)` 判断「队列满」（无缓冲通道恒真）；`defer close` 与显式 `close` 并存 | 三处是**「永不可能」型活锁断言**（未关闭的 `range`、nil 通道、缺 `ctx.Done()` 分支）——条件在数学上永不满足，任何 deadline 都充分；另有 `close of closed channel` 的运行时 `panic`（硬检查）与「收到条数 == 投出条数」的守恒断言 | 输入关闭后 `out` 必须被关闭（`range out` 自然结束）；超时后 `Stream` 返回 `context.DeadlineExceeded`；nil 错误通道被当作「这一路禁用」；无缓冲交接不误判背压 | `select` 的多路随机性与公平性分布 |
| 03 `goroutine-leak-and-context` | `TestRunBatchCancelsWork` / `TestRunBatchReportsFailure` / `TestNoGoroutineLeak` | 子 goroutine 不检查 `ctx.Done()`；worker 阻塞在无人接收的结果通道（泄漏）；子 goroutine 的错误只 `log` 不返回；`WithCancel` 的 `cancel` 没有 `defer`（`go vet` 的 `lostcancel` 会指出来） | 取消后任务体执行次数必须冻结（计数守恒）；`RunBatch` 必须返回非 nil error 且 `errors.Is` 命中；goroutine 数**回落到基线**（泄漏的 goroutine 永不回落 ⇒ 红是确定的） | 取消后在有界时间内返回 `context.Canceled`、不再执行新任务、lane 内 goroutine 数回落、失败批次返回可判定的 error | 泄漏的**根因定位**（数量可判、根因只能看 dump） |
| 04 `sync-primitives` | `TestInitExactlyOnce` / `TestReadersDoNotBlockEachOther` / `TestWarmupWaitsForAll` | 惰性初始化用「if nil 再赋值」而不是保证恰好一次（并发下重复加载）；读路径用互斥锁而非读写锁；`atomic` 累加与裸读混用；`WaitGroup` 在 `Wait` 之后并发 `Add` | 初始化次数 == 1（闸门把 `Load` 挂住，三个 goroutine 必然同时进入判断）；**握手断言**「A 持读锁期间 B 必须能进入」是二值事件；`WaitGroup` 误用会触发运行时 `sync: WaitGroup misuse` | 策略只加载一次且所有并发调用拿到同一个不可变快照；A 持读期间 B 能进入；限额计数守恒；两次预热都等到在飞任务结束 | RWMutex 的吞吐收益、写者饥饿 |
| 05 `gmp-and-pprof` | `TestGoroutineBudgetUnderGate` / `TestQueueBoundReturnsErrQueueFull` / `TestCloseWaitsForInflight` | 一个任务一个 goroutine（无并发上限）；无界队列（`Submit` 从不拒绝）；`Close` 不等在飞任务 | 闸门把 N 个任务挂在「在飞」状态时，goroutine 数是**逻辑事实**（N 对 W，差一个数量级）而非计时事实；容量语义与计数守恒 | 挂起状态下 goroutine 数 ≤ worker 上限 + 常数；队列满时 `Submit` 返回 `ErrQueueFull`；`Close` 返回后被接受的任务全部执行完 | P 的利用率、工作窃取、`GOMAXPROCS` 的实际并行度、抢占时机 |
| 06 `escape-and-gc`（选修） | `TestEncodeAllocBound` / `TestEncodeCorrectAfterGC` / `TestEncodeReuseNoDirtyData` | 每条事件新分配 1 MiB 缓冲；池化实现把 `sync.Pool` 当缓存用（`Put` 后立刻 `Get` 期望命中）；复用前不清空 | `testing.AllocsPerRun` 是**计数**不是计时；测试中途插一次 `runtime.GC()`，池必然被清空 ⇒ 「依赖命中」的实现必然出错（确定性），`sync.Pool.New` 兜底的实现必然正确 | 平均分配次数 ≤ 上界（钉死编译器版本后是确定量）；`runtime.GC()` 之后结果仍正确；被污染的池对象取出后结果仍正确 | `-gcflags=-m` 的输出文本、`GOGC` 的停顿曲线、`sync.Pool` 的命中率 |

**逐条补充（表里放不下的因果）：**

- **stage 01 的红是最硬的一条**：`concurrent map writes` 由运行时无条件编译进去（不是 `-race` 才有的检查），所以即使有人把插桩关掉、或忘了加 `-race`，只要两个 goroutine 真的同时进了写路径，进程就会以 `fatal error` 终止——也就是说这条锚点不依赖探测器。代价是「同一个测试包里会 `throw` 的场景」会**终止整个测试二进制**，因此判定单位是**包级 PASS/FAIL**（`go test` 会把它报成 FAIL + 非零退出），`expect` 文案里明说「骨架上的红可能是 panic 而不是断言失败」。另一个后果：会 `throw` 的场景与普通断言场景必须分到**不同的测试函数**，报告里才能看出「到底红了哪几条」。
- **stage 02 的红是最多确定性锚点的一条**：五处缺陷里有四处是「条件永不满足」型——未关闭的 `range` 永远等下去、nil 通道永远不就绪、缺 `ctx.Done()` 的 `select` 永远收不到取消。这类断言与「快慢」无关：任何 deadline 都充分（我们统一用 3s），因为**正确实现会在毫秒级返回，错误实现会永远不返回**。这是把「活锁」变成确定性判据的关键写法，规格里把它固化成 `testkit.Deadline(t, d)`。
- **stage 03 的泄漏检测必须双向确定**：红是确定的（泄漏的 goroutine 永远不回落，等到超时必然是红），绿需要一个**结算窗口**（正常返回的 goroutine 可能还没被回收）——所以实现是「以 2s 为上限轮询，直到 goroutine 数回落到基线；超时即红」。这个 2s 不是性能阈值，它是「等待一个必然发生的事件」的余量，实际上正常实现是微秒级回落；规格里要求窗口至少是实测回落时间的 100 倍，宁慢勿假红。
- **stage 04 的握手断言是「把计时问题变成事件问题」的样板**：不测「读得多快」，而测「A 持读锁期间 B 能不能进入」——正确实现（读者并发）**必然**允许，错误实现（互斥）**必然**不允许，事件是否发生是二值的。要让它成立，夹具必须能把 A 挂在持锁状态里：做法是把策略来源做成接口（`PolicySource`，骨架已绑好、不许改），测试注入一个会阻塞的 `Load`，于是「持锁窗口」变成可控事件，不需要往业务代码里塞 hook。
- **stage 05 的 goroutine 上界是逻辑事实**：测试提交 N=200 个任务，任务体第一步就是阻塞在测试自己的闸门上（闸门在**测试的闭包**里，不在业务代码里）。于是「200 个在飞任务」是一个确定的挂起状态：正确实现此刻只有 W（例如 8）个 worker goroutine 活着，骨架里则有 200 个。断言是「多次采样取最大值 ≤ W + 常数」——因为所有任务都被闸门按住了，不可能有任务偷偷完成，采样的最大值也是逻辑事实。`GOMAXPROCS=2` 下照样跑，只是不判并行度。
- **stage 06 是选修，因为它唯一一条判据与工具链绑定**：分配次数是确定量（同一编译器版本下逐次一致），但它随 Go 补丁版本变化，所以它必须靠 `go.mod` 的 `toolchain` 行 + 可选的镜像摘要 pin 才站得住。真正**不依赖版本**的部分是另外两条：`runtime.GC()` 之后仍正确、被污染的池对象取出后仍正确——它们才是这一阶段进 canonical 的主判据。

### 1.4 「红在对的地方」的排除法

平台准入门最怕的红是「红在一个跟代码无关的地方」。本 Track 逐条排除：

- **不是编译错**：骨架必须能构建，`scripts/build.sh`（= `go build ./...`）在准入门里跑。
  注意 `go vet` **故意不在** build 路径里——骨架上的 `copylocks` / `lostcancel` 报警是**设计意图**（它们是最好的发现线索，见 §2.3），把 vet 塞进 build 会让「骨架可构建」这一项直接失败。
- **不是脚本为空 / 用例没被跑到**：`scripts/test-stage.sh` 是判定面内的唯一入口，它会先用 `-run '^$'` 做一次 `-race` 编译探针（探针失败就 exit 2，并打印「本 Track 的判定需要 -race（需要 C 编译器）」），再用 `go test -json` 统计实际收集到的用例数；**用例数为 0 一律 exit 3 判为「判定不成立」**，而不是当成绿。
- **不是装配失败**：`smoke` 在骨架上必须是绿的——它构造组合根并跑一条单线程的 happy path，不碰任何并发缺陷。它绿，说明骨架的类型装配与 API 形状是通的。
- **不是基础设施没起来**：本 Track **没有基础设施**。这一条对照 seckill-lab 是实打实的优势——那边「MySQL 没起」会把一次红污染成一片，判据的可读性要靠人分辨。
- 结论：骨架的红只能来自 §2.4 那张缺陷矩阵里的 planted 缺陷；每个 stage 的「红在哪一条断言」要在实测证据报告里逐条记录（`TASKS/evidence-stages-01-06/REPORT.md`，照 seckill 的 `TASKS/evidence-*` 的做法）。

### 1.5 把抖动变确定的五类锚点（本 Track 的公共手法）

| 类别 | 确定性来自 | 用在哪 |
|---|---|---|
| (a) 运行时硬检查 | 不是 TSan，是 runtime 自带的不变量：`concurrent map writes` / `send on closed channel` / `close of closed channel` / `sync: WaitGroup misuse`。两个 goroutine 真的进了同一段临界区就必然触发 | 01、02、04 |
| (b) 「永不可能」型活锁断言 | 条件在数学上永不满足（未关闭的 `range`、nil 通道、缺 `ctx.Done()`）⇒ 任何 deadline 都充分，与快慢无关 | 02、03 |
| (c) 交互式握手 | 把「谁比谁快」换成「事件是否发生」：正确实现必然允许、错误实现必然不允许，二值 | 04 |
| (d) 闸门下的并发上界 | 任务体被测试自己的闸门按住 ⇒ 在飞数量是确定的挂起状态，goroutine 数是逻辑事实而非计时事实 | 03、05 |
| (e) 计数守恒 / 分配计数 | 接受数、执行数、编码字节数必须一一对应；`AllocsPerRun` 是计数不是计时 | 01、02、03、05、06 |

五类里只有 (d) 的**绿侧**需要结算窗口（等一个必然发生的回落），其余四类的红绿两侧都是二值。

### 1.6 只能「可观测」、不进 canonical 的考点

这些不是不重要——它们是八股面试的真实考点，只是**没有稳定到能当判据**。规格把它们全部安置在 `acceptance/soak/`（`runtime.sim` 指向的目录，与正确性门**分开评级**，设计 §7.5）与 `TASKS/*.md` 的观察练习里，产出证据而不产出红绿：

| 考点 | 为什么不进 canonical | 安置 |
|---|---|---|
| `select` 多路就绪时的随机性与公平性 | 只承诺「随机选」，不承诺分布；断言分布必然是 flaky | `soak` 里跑 1 万次统计，只作观察 |
| 工作窃取、P 的利用率、抢占时机 | 依赖宿主核数与调度抖动，没有稳定可观测 API | `soak` 的 `runtime/trace` 产出 `trace.out`，答辩时用 `go tool trace` 看 |
| `GOMAXPROCS` 的实际并行度 | 容器里默认读宿主 CPU 数，同一份代码在不同机器上并行度不同 | 只判「功能在 `GOMAXPROCS=2` 下仍正确」，不判并行度 |
| RWMutex 的吞吐收益、写者饥饿 | 是相对性能，依赖机器与负载形状 | `soak` 的 benchmark 相对值，仅观察 |
| `sync.Pool` 的命中率 | GC 说了算，同一进程内都不可预测 | 只判「未命中时仍正确」 |
| `-gcflags=-m` 的逃逸决策文本 | 输出文本随 Go 补丁版本变（措辞、层级都会变） | `TASKS/stage-06` 的观察命令；canonical 用 `AllocsPerRun` 代替 |
| `GOGC` / `GOMEMLIMIT` 的停顿曲线 | 绝对耗时的抖动指标 | `soak` 的 `GODEBUG=gctrace=1` 输出 + benchmark 相对值 |

### 1.7 不可判定 / 需要妥协的考点（诚实清单）

- **「锁粒度是否最优」「channel 还是 mutex」是设计判断**，不是红绿判据。canonical 只判可判的子集（不变量是否守住、读者是否被写者误伤），其余进 `submission.require` 的答辩与人工/评审环节。
- **泄漏的根因**不可判，只有「有没有泄漏」「回落到基线没有」可判。
- **`-race` 的完备性**不可判：它能证明「报了就有」，不能证明「不报就没有」。规格的处理是不假装它能，而是用 §1.5 的五类锚点补上非探测器的确定性。
- **单核机器**是本 Track 唯一一处平台相关的残余不确定性：stage 01 的运行时 map 检查需要真并行才触发（多核默认成立）。处理办法是把 `cpu: "2"` 写进 `manifest.requires`，让环境体检能提前提示；同时判据的第一层仍是探测器（它不需要并行），所以单核机器上骨架**照样红**，只是少了一条独立锚点。这条不在同一台机器上反复跑就看不出来，所以必须写进风险表而不是藏起来。
- **判据命令的平台侧未知**：准入门目前的判别性经验来自 `mvn -Dgroups`，Go 侧需要门能按 `test_group` 映射到包路径并加 `-race`。本规格的应对是把判定命令固化在 `scripts/test-stage.sh`（判定面内），并让测试在**没有** `-race` 时仍能靠结构性锚点给出正确的红绿（所以即使门不带 `-race`，判别性检查也是对的）；fail-closed 的检查放在脚本入口而不是测试里，避免门把「参考解不绿」误判。这一条列为开工前置校验（§8）。

### 2.2 分层与约定

**lane 正交（本 Track 最重要的骨架约定，直接决定「红在对的地方」）**

六条 lane 一一对应六个 stage：`quota`（01）/ `dispatch.pipeline`（02）/ `dispatch.worker`（03）/ `limit`（04）/ `sched`（05）/ `pool`（06）。

1. **lane 之间不互相调用**。组合根 `internal/gateway` 负责装配，它把 `config.Snapshot`（构造期定下的只读值）分发给各 lane；除此之外，lane 之间不共享任何可变状态。这样某个 stage 的 canonical 测试只驱动本 lane 的入口，同分支上别处的骨架缺陷对它**是睡着的**——`acceptance/stage01` 只 import `quota`，`go test ./acceptance/stage01/...` 连 `dispatch` 都不编译。
2. **为什么这条约定必须写在 `docs/架构与约定.md` 里**：分支链的基线是「Stage 1..NN 全都未修复」，如果 lane 之间互相调用，stage 03 的测试会先踩到 stage 01 的 map 缺陷（进程直接被 `throw` 干掉），红是红的，但红在别人的缺陷上——判别性门照样过，教学质量塌了。lane 正交是让「红在对的地方」在链式分支下仍然成立的那个结构性前提。
3. **同一包内也不互相调用**：`dispatch/pipeline.go` 与 `dispatch/worker.go` 同属 `dispatch` 包，但 `Runner` 不经过 `Pipeline`、`Pipeline` 也不起 `Runner`。同包只是共享 package 名，不是共享路径。

**导出 API 就是判据的接触面**（外部测试包只能碰这些；形状一旦定下就是契约，写进 `docs/架构与约定.md` 第 2 节）：

```
quota:    NewRegistry() *Registry; (*Registry) Grant(user, activity string) (Grant, error)
          (*Registry) GrantsFor(user string) []Grant; (*Registry) Total() int
          NewCounter() *Counter; (*Counter) Inc(); (*Counter) Value() int
dispatch: NewPipeline(Options) *Pipeline; (*Pipeline) Stream(ctx, in <-chan Event, out chan<- Result) error
          NewRunner(Options) *Runner; (*Runner) RunBatch(ctx, tasks []Task) error; (*Runner) Close() error
limit:    PolicySource 接口（骨架已绑好，不许改）+ NewLimiter(PolicySource, Options) *Limiter
          (*Limiter) Policy() Policy; (*Limiter) Acquire(n int) bool; (*Limiter) Warmup(ctx, n int) error
sched:    NewScheduler(Options) *Scheduler; (*Scheduler) Submit(ctx, Task) error  // 队列满 → ErrQueueFull
          (*Scheduler) Close(ctx) error; (*Scheduler) Stats() Stats
pool:     NewEncoder() *Encoder; (*Encoder) Encode(ev Event) []byte
          // 返回的切片只在「下一次 Encode 之前」有效（池化契约，写在架构约定里）
```

**判定命令唯一**（写进 `docs/架构与约定.md` 与 `Makefile`，`test_group` 只是一个 token）：

| `test_group` | 展开成 | 用途 |
|---|---|---|
| `stageNN` | `go test -race -count=1 -timeout=90s ./acceptance/stageNN/...` | canonical 红绿判据 |
| `smoke` | `go test -race -count=1 ./smoke/...` | 环境体检（含 `-race` 可用性） |
| `soak` | `go test -race -count=1 -timeout=15m ./acceptance/soak/...` | 长跑 / 归因，与正确性**分开评级** |
| `all` | `go test -race -count=1 ./acceptance/...` | `main` 上的整体体检（骨架全红是正常的） |

- `-count=1` 是必须的：Go 会缓存测试结果，不关缓存就可能拿到上一次的 PASS。
- 判定入口是 `scripts/test-stage.sh`（判定面内），它强制 `-race`、先做编译探针、再统计用例数（0 个用例 → exit 3）。
- `testkit.RaceEnabled`（由 `//go:build race` / `!race` 两个文件给出）只用于**在报告里标注这一跑有没有探测器**，不作为 fail 条件——这样即使平台的判别性检查不带 `-race`，红绿仍然正确（靠 §1.5 的结构性锚点），而「忘了 `-race`」这件事由脚本入口 fail-closed 拦住。

### 2.3 构建与摘要约定（Go 版的脚手架口径）

**`go.mod`**

```
module github.com/OnlyblackTea/go-concurrency-lab

go 1.22
toolchain go1.22.x        // 钉到当时最新的 1.22 补丁版（例如 go1.22.6）

// require 段必须为空：本 Track 的硬约定是「只用标准库」。
```

为什么连补丁版都要钉：**判据本身依赖工具链**——race 运行时的实现、逃逸分析决策、`AllocsPerRun` 的数值都随补丁版本变。`toolchain` 行让「学员跑的是哪个编译器」从口头约定变成文件里的一行；`scripts/verify-deps.sh` 另外审计两件事：`go.mod` 里没有 `require` 段、`go.sum` 不存在（零第三方依赖的可验证口径）。

**`Makefile`**（学员入口；每个目标都对应一条文档里写死的命令）

| 目标 | 展开 | 性质 |
|---|---|---|
| `make build` | `bash scripts/build.sh` → `go build ./...` | 准入门「骨架可构建」的稳定调用点 |
| `make vet` | `go vet ./...` | **工具，不是门**（见下） |
| `make test PKG=acceptance/stage01` | `bash scripts/test-stage.sh stage01` | 判定入口（带 `-race`） |
| `make test-norace` | 不带 `-race` 的对照跑 | 只用于观察「没有探测器时会漏掉什么」 |
| `make smoke` / `make soak` | `test-stage.sh smoke` / `soak` | 体检 / 长跑 |
| `make digest` | `bash scripts/digest-pin.sh` | 重算 pin（改过 runtime 指向的文件就重跑） |

**`go vet` 为什么故意不进 build 路径**：骨架的缺陷会**真实地**触发 vet 的 `copylocks` / `lostcancel` 等分析器。这不是要绕过 CI，而是把它当成发现线索——「`go vet` 指到哪一行」本身就是本 Track 教学的一部分（真实 Go 工程里就是这么定位并发与生命周期问题的）。代价是 vet 会削弱一部分难度，规格把它记进风险表（§7）：如果某道题被 vet 一句话说穿，就换缺陷形状，而不是把 vet 关掉。
CI 侧对应地**不能把 vet 当 gate**——门只认 `scripts/build.sh` 与 `scripts/test-stage.sh`。

**是否要 docker：默认不要，容器是可选的复现档位。**

| 档位 | 前置 | 得 | 失 |
|---|---|---|---|
| 默认（本机 Go） | `go 1.22+` + cgo/C 编译器 | 冷启动 0、无需镜像、判据全在进程内 | 工具链版本靠 `go.mod` 的 `toolchain` 行与体检，不是物理锁定 |
| 容器档（可选） | `docker 24` | 工具链**物理**锁定到 `golang:1.22.x-bookworm@sha256:...`，`-race` 与分配上界完全可复现 | 要装 docker、要拉镜像 |

两档共用同一套命令，容器档只是把 `go` 换成 `docker/run-in-toolchain.sh` 的包装。**digest_pin 仍然必有**（见 §6）：锁的是 `build` / `tests` / `sim` 三个入口的文件树摘要、`go.mod`（含 `go`/`toolchain` 行）、以及容器档位的**工具链镜像摘要**——镜像摘要同时写在 Dockerfile 的 `FROM ...@sha256:` 里（保证构建真用它）和 `track.yaml` 的 `digest_pin` 里（保证构建脚本没被换过）。

**`scripts/` 三个脚本的职责**（都在判定面内）：

- `build.sh`：`exec go build ./...`（不加 `-race`、不跑 vet；只回答「骨架能不能构建」）。
- `test-stage.sh`：唯一判定入口。三件事——① `-race` 编译探针（`go test -race -run '^$' ./smoke/`），失败即 exit 2 并给出「Windows 需要 gcc、Linux 需要 gcc/clang」的提示；② 跑 `go test -race -count=1 -timeout=90s ./acceptance/<group>/...`；③ 用 `-json` 统计用例数，0 个 exit 3。**它决定「加不加 `-race`」，所以除了判定面声明之外，还要给它一条整目录的 Merkle pin**（见 §6）。
- `digest-pin.sh`：沿用 seckill 的配方（目录递归/glob 展开 → 每文件 CRLF→LF 归一化后取 sha256 → 按相对路径 C 序排序拼 `<sha>  <path>\n` → 再取一次 sha256），入口清单从 `track.yaml` 的 `runtime` 段自解析；**唯一改动是把「镜像 ref 从 docker-compose.yml 解析」换成「从 `docker/go-toolchain.Dockerfile` 的 `FROM ...@sha256:` 行回读」**（本 Track 没有 compose）。

### 2.4 故意留的缺陷（正交缺陷矩阵）

| stage | 文件 | 缺陷（骨架里长什么样） | 触发它的现象 | 锚点类别 |
|---|---|---|---|---|
| 01 | `internal/quota/registry.go` | `grants map[string][]Grant` 的读写没有任何同步；`Grant` 是「先查重、再 append」的两步复合操作 | `fatal error: concurrent map writes` / 同用户重复发放 | (a) + (e) |
| 01 | `internal/quota/counter.go` | `type Counter struct{ n int }`，`Inc()` 做 `c.n++`，`Value()` 裸读 | 计数 < 实际发放次数；`-race` 报同一地址的无序读写 | (e) + 探测器 |
| 02 | `internal/dispatch/pipeline.go` | `for ev := range in` 结束后不关闭 `out`；`select` 只有 `in` 与超时两个 case；nil 错误通道被直接塞进 `select`；用 `len(ch)==cap(ch)` 判断队列满；`defer close(out)` 与显式 `close(out)` 并存 | 消费者 `range out` 永久阻塞 / 取消后不返回 / `panic: close of closed channel` / 无缓冲通道被误判为满而丢事件 | (a) + (b) + (e) |
| 03 | `internal/dispatch/worker.go` | 子 goroutine 用父 ctx 但不检查 `ctx.Done()`；worker 向无接收者的 `resultCh` 发送；子 goroutine 的错误只 `log`；`context.WithCancel` 的 `cancel` 没有 `defer` | 取消后批次仍在跑 / goroutine 数不回落 / 失败批次返回 nil | (b) + (d) + (e) + `go vet lostcancel` |
| 04 | `internal/limit/limiter.go` | 惰性初始化写成「if nil 再赋值」；读路径用互斥锁；`atomic.AddInt64` 与裸读混用；`Warmup` 在 `Wait` 之后并发 `Add` | 策略被加载多次且结果不一致 / 两次读互相阻塞 / 计数错 / `sync: WaitGroup misuse` | (a) + (c) + (e) + 探测器 |
| 05 | `internal/sched/scheduler.go` | `Submit` 直接 `go task()`（一任务一 goroutine）；待办任务存在无上限切片里；`Close` 不等在飞任务 | 8 万条导入把进程打爆 / `Submit` 从不拒绝 / `Close` 后任务丢失 | (d) + (e) |
| 06 | `internal/pool/buffer.go` | `Encode` 每次 `make([]byte, 0, 1<<20)`；池化分支把 `Put/Get` 当缓存用且不复位 | 分配字节数与 GC 频率十倍于必要 / `runtime.GC()` 之后内容错 | (e) + 强制 GC |

**每个缺陷的"睡着"论证**（这是 §1.4「红在对的地方」在链式分支下的落地）：

| stage 的测试只驱动 | 同分支上睡着的缺陷 | 为什么睡着 |
|---|---|---|
| 01 → `quota` | dispatch / limit / sched / pool 的缺陷 | 测试包不 import 那些包，编译期就不进图 |
| 02 → `Pipeline.Stream` | `worker.go` 的泄漏、`quota` 的竞争 | 同包不等于同路径：`Stream` 不构造 `Runner` |
| 03 → `Runner.RunBatch` | `pipeline.go` 的挂死 | `Runner` 不经过 `Pipeline` |
| 04 → `Limiter` | 其余全部 | lane 之间只共享只读 `config.Snapshot` |
| 05 → `Scheduler` | 其余全部 | 同上 |
| 06 → `Encoder` | 其余全部 | 同上 |

### 2.5 基础设施

**没有。** `runtime` 不声明 `compose`，也不 pin 任何服务镜像：不开端口、不起容器、不联网，`go test` 全程在进程内。这是本 Track 相对 seckill-lab 的成本优势（学员机器零常驻内存、CI 不用等 healthy），也是 §1.4「基础设施没起来」这一类污染红在结构上不可能出现的原因。
唯一的宿主前置是工具链与 `-race`（cgo + C 编译器）；可选容器档位用 §2.3 那张表的第二档，镜像摘要进 `digest_pin`。

### 2.6 冒烟测试

`smoke/` 是 stage-00（board-only，**不出 ticket**、无分支）的落点，骨架上必须**绿**：

- `env_smoke_test.go`：构造 `config.Snapshot` → `gateway.New(...)` → 跑一条**单线程** happy path（发一个名额、跑一个小批次、编码一条事件），断言装配与 API 形状是通的。它不碰任何并发缺陷 ⇒ 骨架上天然绿（与 seckill 的 `SmokeTest` 同一个角色）。
- `race_enabled_test.go` / `race_disabled_test.go`：用 `//go:build race` / `//go:build !race` 两个文件给出 `raceEnabled` 常量。**无 `-race` 时这一条响亮地失败**，并打印「本 Track 的判定需要 -race：请确认 CGO_ENABLED=1 且本机有 C 编译器（Windows 上需要 gcc/mingw-w64）」。
  它为什么可以红：stage-00 不是考核工单，它的红含义是「环境不合格」，不是「你没做完」——这与 `stages/README.md` 里对 stage-00 的处理一致。**但要注意**：如果平台的门把 `go test ./...` 整体当判别性输入，这条会污染结果；处理办法（写进 §8 前置校验）是让门按 `test_group` 逐包跑，或在整体跑时排除 `smoke`。

### 2.7 防剧透边界

- **阶段分支里没有任何实现**：`stage-NN-<name>` = 骨架（Stage 1..NN 全部未修复）+ 截至本阶段的验收测试。学员在自己那条 `dev` 上累积实现，合并 `origin/stage-NN` 只多一个测试目录（**只加不删**，不会与他的实现打架）。
- **答案只在 `-sol` 旁支上**：`stage-NN-<name>-sol` 从同阶段 base 切出，内容 = base + 截至该阶段的参考实现（lane 01..NN）。`solutions` 是全阶段总参考，**不作为任何 stage 的 base/head**。
- **`acceptance/stageMM`（MM > NN）在 `stage-NN` 分支上不存在**——后续阶段的判据不在学员工作区里，这一条由分支链本身保证（不需要额外机制）。
- **`TASKS/stage-NN.md` 只放叙事与观察命令**，不放实现、不复述判据（事实只在 `ticket.yaml` 里存一份，照 seckill 的分工）。
- **`internal/` 里不放注释形式的解法提示**；骨架代码的注释只解释「这条 lane 在服务里负责什么」，不解释「哪里可能坏」。

### 2.8 本地跑法（三条命令）

```bash
make smoke                              # ① 环境体检：-race 真的可用吗（无 race 时这一条会响亮地失败）
make build                              # ② 骨架可构建：go build ./...
bash scripts/test-stage.sh stage01      # ③ 单阶段判定：go test -race -count=1 ./acceptance/stage01/...
```

改完代码交卷前，把 ② ③ 各重跑一次，另加 `make vet`（可选，看编译器帮你发现了什么）。

**教学顺序为什么是这样。**

前四关是一条**严格线性**的坡度：先认清「什么叫竞争、探测器怎么判」（01），再学 Go 独有的通信模型——channel 的收发/关闭/选择语义（02），然后是把「取消」这条控制流穿过整条调用链、并让 goroutine 有确定的终点（03），最后回到共享内存那一侧，讲清楚几种同步原语的选型边界（04）。这四步的先后不能换：02 的语义判断要用到 01 的 happens-before 词汇；03 的取消传播要靠 02 的 channel 语义说清「谁在等谁」；04 的选型讨论要在「已经知道锁为什么必要、也知道 channel 不是万能」之后才有意义。

**05 与 06 是一个真分叉**：两者都只依赖 04，彼此不依赖。

```
        go-stage-01  (DAG 根)
             │
        go-stage-02
             │
        go-stage-03
             │
        go-stage-04
          ┌──┴──┐
   go-stage-05  go-stage-06
   GMP 调度/pprof  逃逸/GC（选修）
```

05 讲的是**运行时视角**（goroutine 预算、背压、pprof 能不能看见），06 讲的是**内存视角**（逃逸分析、分配成本、GC 调优），一个走调度器、一个走分配器，交集只有 04 里的同步原语与对象复用。允许学员只做 05 就停（06 是选修，且它唯一一条与工具链绑定的判据风险最高）。

**注意区分「解锁 DAG」与「分支链」**：`progression` 是一棵可以分叉的 DAG（05/06 是兄弟），但**分支仍然是一条链**——`stage-06` 从 `stage-05` 切出。原因是 `stages/README.md` 那条契约：分支是**发布单位**，必须只加不删地叠上去，否则学员合并 `origin/stage-06` 时会把 stage-05 的测试当成「删除」丢掉。两个命名空间各管一件事，别混。

```bash

git checkout -b stage-01-data-race main
git rm -r acceptance/stage02 acceptance/stage03 acceptance/stage04 acceptance/stage05 acceptance/stage06
git commit -m "chore(stage01): 链的起点，只保留本阶段验收测试"      # 建链时唯一一次「减」
git checkout -b stage-02-channel-semantics stage-01-data-race
git checkout main -- acceptance/stage02 && git commit -m "test(stage02): 新增本阶段验收测试"

git checkout main -- acceptance/stage03 && git commit -m "test(stage03): 新增本阶段验收测试"
# stage-04 / 05 / 06 同理，逐级叠上去

# 2) 参考解：按 lane 拆成 6 个提交维护在 solutions 上，-sol 从**同阶段 base** 切出再叠截至本阶段的实现
git checkout -b stage-02-channel-semantics-sol stage-02-channel-semantics

git commit --allow-empty -m "chore(stage02): 参考解封板（截至本阶段）"
```

```yaml
brief:
  problem: |
    ## 问题背景

    【线上问题｜来自：配额平台 · 优先级 P0】季度配额开放领取的头十分钟，值班同学连着收到两类告警。

    另一类是网关进程**偶发直接退出**：日志最后一行是运行时抛出的 `fatal error: concurrent map writes`，
    重启之后一切正常，于是被当成"机器抖动"压了下去。后来有人用 `GOMAXPROCS=1` 起了一次，
    现象没再出现，团队里就有了"是不是机器太少"的误判——这也让这个问题一直没被真正修掉。

    ## 问题表现

    网关的配额注册表放在 `internal/quota` 里：`Registry` 用一个 map 记住"谁领了哪个活动的名额"，
    `Grant` 的做法是"先查有没有领过、没有再写进去"，另外用一个普通整数累计总发放数。
    这两处都由 HTTP handler 直接调用，而 `net/http` 是每个请求一个 goroutine —— 也就是说，
    在"查"与"写"之间、在"读计数"与"写计数"之间，没有任何东西阻止另一个请求插进来。

    后果分成两类。会崩的那一类是 map 的并发写：Go 的运行时自带一条不变量检查，
    两个 goroutine 同时进入写路径时它会直接终止进程，而不是让数据悄悄错乱——这正是那行
    `fatal error` 的来路，也解释了为什么它"有时出现、重启就好"。不会崩的那一类更麻烦：
    计数的累加和"先查后写"的去重判断都只会安静地算错，最终表现为总数与明细对不上、
    以及同一用户重复拿到名额。`GOMAXPROCS=1` 那次"消失"并不说明问题不在了，
    它只是让两个访问更难真正重叠；访问之间缺失的先后关系一点没变，所以换一台机器、换一个
    负载形状，它照样会回来。

    本题需要修改以下文件：

    - `internal/quota/registry.go`：让注册表在并发读写下的行为有明确的语义，并让"查重"与"写入"这两步
      作为一个整体成立——它们合起来才是一条业务不变量，任何一步单独原子都没有意义。
    - `internal/quota/counter.go`：让计数在并发累加之后仍然给出正确的结果，并说清你为什么选这种手段。

    导出 API 的形状（`NewRegistry` / `Grant` / `GrantsFor` / `Total` / `NewCounter` / `Inc` / `Value`）
    与 `Grant` 的字段都不要改，上层与项目约定（`docs/架构与约定.md` 第 2 节）都按它调用。

    【约束】允许你用任何你认为合适的手段达成上面两件事，包括不改数据结构本身；但**不要**靠调整
    `GOMAXPROCS` 或环境变量把并发压下去，也**不要**用编译指示关掉工具链的插桩——那只是让检查不说话，
    不是让访问变得有序。判据在默认设置下跑，`docs/架构与约定.md` 第 6 节写了这一条项目纪律。

grader:

      Go 运行时自带的不变量检查会直接终止测试进程（`fatal error: concurrent map writes`）——
      它给出的不是"断言失败"而是"进程死掉"，这恰好证明了两个 goroutine 真的同时进了写路径；
```

### Ticket 2 · `go-stage-02`

```yaml
# ticket.yaml —— Stage 2 工单的机器可读权威契约（契约来源同上）。
identity:
  id: go-stage-02
  schema_version: 1
  ticket_version: 1
  stage: 2
  title: 管道挂死与事件丢失

brief:
  problem: |
    ## 问题背景

    【线上问题｜来自：配额平台 · 优先级 P1】补发通道有个拖了很久的毛病：每隔几天就有一条"补发卡住"
    的工单。发生的时候，网关的 `/debug/pprof/goroutine` 里消费者 goroutine 全都停在 `chan receive` 上，
    而生产侧在等一个永远不来的接收者；重启即恢复，所以它一直排在优先级列表的后面。
    更少见也更难解释的是滚动重启时那行 `panic: close of closed channel`：进程直接退出，
    而那一批事件到底处理了多少，事后没人说得清。

    ## 问题表现

    `internal/dispatch/pipeline.go` 里的 `Stream` 是这条通道的中枢：它从 `in` 收事件、投给下游的 `out`、
    并在某些条件下提前收工。现在这套实现把 channel 的几个语义用错了，于是"结束""取消""背压"
    这三件事各自以不同的方式失效。

    先说结束：`in` 被上游关闭之后 `Stream` 自己会退出，但下游消费者的写法是 `for r := range out`——
    一个从不被关闭的 channel 会让 `range` 永远等下去。于是一次已经完成的分发，在消费者眼里变成了
    "还没结束"，这就是那些 `chan receive` 栈的来路。再说取消：`Stream` 的 `select` 只盯着输入与超时，
    没有盯调用方的取消信号，所以上游取消之后它依然挂在那里。然后是关闭纪律：同一个 channel 上
    既有延迟关闭、又有提前关闭，路径重叠时就会撞上运行时的 panic —— Go 对"谁该关闭 channel"
    和"能关几次"这两件事有明确约定，违反它不是风格问题，是会终止进程的。

    还有两处更安静的坑。背压判断用的是"长度等于容量"，这个条件在**无缓冲** channel 上恒为真，
    于是本该同步交接的事件被当成"队列满"丢掉，丢的恰好是双人协作场景下的第一批。最后是可选配置：
    错误通知通道允许留空，而代码把它当成一个普通的 `select` 分支来用 —— 一个 nil channel 在 `select`
    里的含义，和"这个通道没被配置"的含义需要显式对齐，否则那一路永远轮不到就绪。

      `NewPipeline` / `Stream` 的签名与 `Event` / `Result` 的形状不要改。

    有一条顺序约束不是风格偏好：`Stream` 返回之前必须先把它已经收下的事件**全部投出去**。
    如果结束信号早于最后一条事件，消费者看到的是"事件丢了"而不是"流结束了"——而这两种情况在判据里
    必须分得开，判据正是靠它们区分"正常收尾"与"提前退出"。

    另一条边界约束：不要靠"给每条 channel 都塞上缓冲"让挂死看起来消失。容量只是把阻塞推迟到第 N 条
    事件，而"谁负责关闭""什么时候算结束"这些语义一点没变；判据会用无缓冲与容量为 1 两种形状各跑一遍。
```

```yaml
    ## 问题背景

    【线上问题｜来自：配额平台 · 优先级 P1】限额策略（每个活动的额度上限与放行规则）本该在网关启动时

    额度，那几分钟里有一部分请求按旧上限被放行了，月底对账才发现。另一个现象是"查限额变慢了"：
    限额查询本身是只读的，却在压力下互相排队，P99 抖动明显，而策略数据在这期间一次都没变过。

    ## 问题表现

    `internal/limit/limiter.go` 的 `Limiter` 做两件事：把策略加载进来，以及拿着策略判断一次请求能不能放行。

    加载这一处写的是"先看字段是不是空的，是空的就加载并赋值"。这在单线程下等价于"只做一次"，
    并发下却有两个毛病：多个 goroutine 可以同时看到"还是空的"，于是各自加载一次，谁后写进去谁算数；
    而"加载并赋值"这个复合动作本身也不是一个整体，中途被别的 goroutine 读到的那个半成品
    会被当成已就绪的策略用掉。

    放行这一处把整条判断链放在互斥的临界区里。策略加载完成之后就是只读的，只读的读之间本不该排队——
    现在它们排了，所以这份抖动不是策略带来的，而是这把锁带来的：粒度太粗，把可以并行的部分串起来了。
    计数那一路另有问题：它把原子累加和普通读取混在同一份数据上。原子只保证**单次操作**不可分割，
    它管不了"另一个地方直接读"这件事——那仍然是一次没有同步的访问。最后，批量预热用到的等待原语
    有个契约：加法必须发生在等待之前。现在的写法把加法放在了等待之后，这要么触发运行时对误用的检查，
    要么让等待提前放行、把"还没跑完"当成"跑完了"。

    ## 你需要完成的修改

    本题需要修改以下文件：

    - `internal/limit/limiter.go`：让策略加载在并发下**恰好发生一次**，且第一次之后的所有调用看到的是
      同一份不可变快照；让只读的读之间不再互相排队，同时给将来可能的写路径留出明确位置；
```

```yaml
    `internal/pool/buffer.go` 的 `Encode` 每次调用都新分配一块大缓冲再把内容追加进去。分配本身是必要的

      强制 GC，池必然被清空，于是"依赖命中"的实现必然给出错误结果；正确实现把未命中当成正常情况、
      由对象池的构造器兜底，因此必然正确。其三，复用而不复位会让内容错位：判据先让一块缓冲被上一次
      的编码填满，再检查下一次的结果必须与原内容逐字节相同。

      改对后为【绿】：平均分配次数落到上界之内、批量编码的分配字节数显著下降，同时三条正确性断言
      全部成立——强制 GC 之后结果仍正确、被污染的缓冲取出后结果仍正确、连续两次编码的内容各自独立
      且正确。

      说清这条用例到底在验什么：它验的不是"用了对象池"，而是**"复用了东西"与"结果仍然正确"能不能
      同时成立**。把复用机制当缓存用（依赖命中）、复用前不复位、为了省分配而改掉返回契约，
      三种写法都会让正确性那两条当场失败。
      注：本阶段的红绿与工具链版本绑定（分配次数随补丁版本变），所以它是选修；
      `go.mod` 的 toolchain 行与容器档位的镜像摘要就是它的锁。逃逸分析输出、GC 停顿、命中率
      只作可观测（进 soak 与 TASKS 的观察练习）。
```

````markdown
## Stage 1 · 数据竞争 & race detector ⬜

**亲手场景**：并发领取名额时出现重复发放与 `fatal error: concurrent map writes` → 你列出所有共享访问、让每一对之间都有同步边，并用探测器证明报告消失。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 数据竞争 | 两个 goroutine 访问同一内存位置、至少一个是写、且它们之间没有 happens-before 边 | Go 里什么算数据竞争？它和「竞态条件」是一回事吗？ |
| happens-before | 同步操作（channel、锁、等待组、原子）建立偏序；没有边就没有可见性保证 | 什么时候一个 goroutine 的写一定能被另一个看见？ |
| race detector | 基于 ThreadSanitizer 的动态分析：影子内存 + 向量时钟，报的是「无序访问」而不是「同时访问」 | `-race` 怎么判定竞争？它会不会漏报？ |
| 并发 map 的运行时检查 | map 内部有个「正在写」标志位，已经在写时再进写路径直接终止进程 | 为什么并发写 map 会直接崩，而不是数据悄悄乱掉？ |
| 临界区与不变量 | 锁保护的是不变量的作用域，不是某一行代码 | 怎么划分临界区？锁对象被复制会怎样？ |
| 插桩的边界 | 关掉插桩只是让探测器失明，运行时的硬检查不受影响 | 生产环境能开 `-race` 吗？开销大概多少？ |

**复现命令**：`bash scripts/test-stage.sh stage01`（骨架红 → 改完绿）· 对照观察 `make test-norace PKG=acceptance/stage01` · 稳定性复跑 `go test -race -count=3 ./acceptance/stage01/...`

## Stage 2 · channel 语义 ⬜

**亲手场景**：补发通道挂死、事件被丢、重启时 `panic: close of closed channel` → 你把「结束」「取消」「背压」三件事的语义逐个对齐。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| channel 的两副面孔 | 既是队列又是同步原语，每次收发都建立一条 happens-before 边 | channel 和互斥锁怎么选？ |
| 缓冲 vs 无缓冲 | 无缓冲是同步交接（收发双方必须同时就位），缓冲是异步队列（满了才阻塞） | `make(chan T)` 与 `make(chan T, 1)` 差别在哪？ |
| 关闭语义 | 关闭表示「不会再有值」，应由发送方关；向已关闭的发送、重复关闭都会 panic | 谁该关闭 channel？ |
| range over channel | 只在通道被关闭后结束，否则永久阻塞 | 为什么 `for v := range ch` 会挂死？ |
| nil channel | nil 通道上的收发永久阻塞；放进 `select` 等于禁用这一路 | `select` 里放 nil channel 有什么用？ |
| select 的语义 | 多路就绪时随机选一路；`default` 提供非阻塞分支 | `select` 是公平的吗？怎么做非阻塞发送？ |
| 超时与取消 | 可取消的等待要把取消当成一个分支；热路径上堆定时器会攒出垃圾 | 超时该用 `context` 还是定时器？ |
| 背压 | 容量不是「满」的定义；满要用「发不出去」这件事来表达 | 队列满了应该阻塞、拒绝还是丢弃？ |

**复现命令**：`bash scripts/test-stage.sh stage02` · 观察挂死时 `go test -timeout=10s` 打出的 goroutine dump

## Stage 3 · goroutine 泄漏 & context ⬜

**亲手场景**：点了「取消这批补发」之后 CPU 十几分钟不降、pprof 里几千个 worker 栈 → 你把取消穿过整条调用链、给每个 goroutine 一个确定的终点。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| goroutine 泄漏 | 永久阻塞在收发/加锁/等待上，且再没有引用能唤醒它；它连同栈一直活着 | goroutine 泄漏怎么排查？ |
| 泄漏检测 | 数量看 `runtime.NumGoroutine`，位置看全量栈快照，前后对比并按函数过滤 | 线上怎么定位泄漏？ |
| context 传播 | context 只是一条广播，沿调用链向下传；它自己不中断任何东西 | context 为什么是第一个参数？ |
| 取消的落点 | 只有在会阻塞或耗时的地方检查取消才有效；纯计算不会因为取消而停下 | 哪些地方必须检查取消？ |
| 错误传播 | 批量操作要让调用方拿到可判定的原因，而不是一行日志 | 批量任务失败时返回值该长什么样？ |
| 等待组的契约 | 加法必须早于等待；等待可重入但有明确前提 | `WaitGroup` 能复用吗？它与 errgroup 差在哪？ |
| 优雅关闭 | 停止接受 → 等在飞 → 释放资源；次序错了就丢任务 | 服务关闭时怎么才算优雅？ |

**复现命令**：`bash scripts/test-stage.sh stage03` · 证据 `bash scripts/test-stage.sh soak`（长跑后的 goroutine 数 / block profile）

## Stage 4 · sync 原语选型 ⬜

**亲手场景**：限额策略被加载了三次、只读查询互相排队 → 你按「原语契约」而不是「习惯」重新选型。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 互斥锁 vs 读写锁 | 读写锁让读者并发，代价是写者可能饥饿、实现更重；只在读远多于写时才划算 | 读写锁什么时候反而更慢？ |
| 一次性初始化 | 「恰好一次」是一种语义，不是「先查后写」；第一次之后所有调用必须看到同一份数据 | 双检锁在 Go 里为什么容易写错？ |
| 锁粒度 | 粒度太细锁不住复合操作，太粗把可并行的部分串起来 | 怎么决定临界区的大小？ |
| 原子操作的边界 | 原子只保证**单次操作**不可分割；混用原子与非原子访问照样是竞争 | 原子操作能替代锁吗？ |
| 内存模型 | 每个同步原语都建立 happens-before；没有它就没有可见性保证 | 为什么本地能跑对、探测器说错？ |
| 不可变快照 | 只读数据一旦发布不再修改，读者之间就不需要互斥 | 怎么让读路径彻底无锁？ |

**复现命令**：`bash scripts/test-stage.sh stage04`

## Stage 5 · GMP 调度 & pprof ⬜

**亲手场景**：80 万条导入把进程打爆、提交接口从不拒绝 → 你给并发一个上限、给压力一条回传路径，并用 pprof 看见它。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| G / M / P | P 持有本地运行队列，M 是内核线程，阻塞的系统调用会让出 P | GMP 分别是什么？ |
| 工作窃取 | 本地队列空时从全局或别的 P 偷一半，兼顾局部性与负载均衡 | 调度器怎么避免负载不均？ |
| GOMAXPROCS | 同时执行 Go 代码的 P 数量；容器里默认读到的是宿主核数 | 容器里它为什么不准？ |
| goroutine 预算 | 每个 goroutine 都有栈、调度与 GC 成本，必须有并发上限 | 一任务一 goroutine 的代价是什么？ |
| 背压 | 有界队列 + 可观察的拒绝，把压力回传给调用方 | 队列该不该无界？ |
| pprof 三件套 | goroutine 看「谁在等」、block 看「等在哪」、mutex 看「锁争用」 | 线上卡顿先看哪个 profile？ |
| runtime/trace | 时间线上看 P 的利用与 goroutine 的阻塞/唤醒 | trace 与 pprof 分别解决什么？ |

**复现命令**：`bash scripts/test-stage.sh stage05` · `bash scripts/test-stage.sh soak` · 用 `go tool pprof -http=:0 <dump>` 与 `go tool trace <trace.out>` 亲手看

## Stage 6（选修）· 内存逃逸 & GC ⬜

**亲手场景**：对账批量编码时 GC 吃掉三分之一 CPU → 你把「每次分配一块大缓冲」变成有上界的复用，并证明复用之后结果仍然正确。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 逃逸分析 | 编译器证明变量不逃出函数才放栈；返回指针、存进接口、被闭包捕获都会逃逸 | 什么情况下变量会分配到堆上？ |
| 分配成本 | 每次分配都要付分配器 + GC 扫描的账；大块分配把堆直接推高 | 怎么判断一个函数有没有多余分配？ |
| 分配计数 | 测「每次调用分配几次」比测耗时稳定得多，它是计数不是计时 | 为什么不要拿耗时当性能判据？ |
| 临时对象池语义 | 它随时可能被清空，不是缓存；未命中必须由构造器兜底 | 池化一定能提升性能吗？ |
| 复用与复位 | 复用的前提是把上一次的状态清干净，否则结果错位 | 复用缓冲区最容易踩的坑是什么？ |
| GC 调优 | 增长倍率与内存软上限各自控制什么；日志里该看哪几个数 | GC 日志怎么看？ |

**复现命令**：`bash scripts/test-stage.sh stage06` · 观察 `go build -gcflags=-m ./internal/pool/` 与 `GODEBUG=gctrace=1 bash scripts/test-stage.sh soak`
````

**负例核对（这个坑真踩过，seckill 的 stage-06 也踩过）**：如果把标题写成 `## Stage 6 · 内存逃逸 & GC ⬜`（去掉「选修」），锚点会变成 `#stage-6--内存逃逸--gc-`——与上表那一行**不相等**，`bagu_map_anchor` 门会响亮地失败。所以：**标题里不要用全角括号包修饰词**（它会被整块丢掉、把相邻字符粘起来），要么把「选修」融进正文句子，要么接受粘连形式并让 ticket 里那句演算与它逐字一致。本规格选择与 seckill 一致的视觉风格（`（选修）` 保留在地图标题里），并把上面那句逐步演算**原文抄进 `go-stage-06` 的 `bagu_map_ref` 注释**，避免下一个人手算错。

**附：本项目不涉及、但该文字了解的考点**（正文里的那节）——沿用 seckill 的做法，把 `synctest`、第三方泄漏检测库、`unsafe`、`LockOSThread`/cgo、netpoller、内存模型原文这些都放进去，避免范围膨胀：它们只出现在地图末尾，不进任何 ticket 的 `concepts`，也不进 canonical 测试。

### 判定面逐条论证

准入门会校验**每条声明都真能匹配到骨架里的东西**（`_CONTRACT.md` §4：「写错一个字母就是静默漏洞」），所以下面第四列是开工时的核对口径：

| 路径 | 为什么判据依赖它 | 学员改了会怎样 | 在骨架里匹配到什么 |
|---|---|---|---|
| `./acceptance/` | **它就是判据**：canonical 测试 + `testkit` 夹具（闸门、开始闸门、deadline、泄漏检测、强制并行） | 删掉一条断言、把 `testkit.Deadline` 的时限改大、把 `Gate` 改成不阻塞——全都等于改判据 | `acceptance/testkit/` + `acceptance/stage01..06/` + `acceptance/soak/`（开工核对：`go list ./acceptance/...` 必须列出 8 个包） |
| `./smoke/` | 环境体检是判据的前置：`-race` 不可用时整条 Track 的判定不成立 | 把体检改成永远通过，可以让「环境不合格」看起来合格 | `smoke/doc.go`、`smoke/env_smoke_test.go`、`smoke/race_enabled_test.go`、`smoke/race_disabled_test.go` |
| `./go.mod` | 它决定**判据用哪个编译器**（`go` 与 `toolchain` 行），也决定依赖闭包 | 换掉 toolchain 行 = 换掉判据（race 运行时、逃逸决策、分配计数全变）；加一个 `require` = 引入第三方代码 | 文件本身（`go mod init` 生成） |
| `./Makefile` | 学员入口，`-race` 写在目标里 | 把 `-race` 从目标里摘掉，就能在「没有探测器」的模式下跑判据 | 文件本身 |
| `./scripts/` | `test-stage.sh` 是**唯一判定入口**（决定加不加 `-race`）；`build.sh` 是准入门入口；`digest-pin.sh` 是摘要来源 | 改判定入口等于改判定规则本身 | `build.sh`、`test-stage.sh`、`digest-pin.sh`、`verify-deps.sh` |
| `./docker/` | 容器档位的工具链定义：改 `FROM` 行就换掉了学员实际使用的工具链 | 换成一个没有 `-race` 支持的镜像，或换一个补丁版让分配上界失效 | `docker/go-toolchain.Dockerfile`、`docker/run-in-toolchain.sh` |
| `./.github/` | CI 跑的就是判别性门 | 改 CI = 改「谁来跑门、跑不跑」 | `.github/workflows/validate-track.yml`（开工时建） |

**刻意不放进判定面的三处**（对照「只放判据依赖的东西」）：

- `internal/` 与 `cmd/`：这是**学员改动面**。放进去工单就没法完成，而且会把「改错文件」升级成「作弊」——这是判定面最容易犯的过度声明。
- `docs/`：八股地图与架构约定是**内容资产**，由内容仓的准入门（`bagu_map_anchor` 解析）保护，不由运行时判定面保护；两个保护机制各管一层，别混。
- `TASKS/`：叙述视图，不是判据。

**`./go.sum` 为什么不声明（一个必须实测的取舍）**：Go 只在存在第三方依赖时才写 `go.sum`，而本 Track 的硬约定是零依赖 ⇒ 它**本就不存在**。判定面的硬门要求每条声明都能匹配到东西，声明一个不存在的路径既是静默漏洞又是硬失败，所以默认不声明它。开工第一步要实测：若 `go mod tidy` 在实践中确实生成了 `go.sum`（哪怕是空文件），就必须把它一并声明并放进判定面——「零依赖」这个约定本身也要靠 `verify-deps.sh` 的可验证口径来守。

### 必须 pin 的东西

| pin 键 | 锁的是什么 | 由谁生成 | 为什么必须锁 |
|---|---|---|---|
| `build` | `./scripts/build.sh` | `digest-pin.sh` | 准入门「骨架可构建」的入口，也是学员最常改的脚本 |
| `tests` | `./acceptance/stage*/`（Merkle 树摘要） | `digest-pin.sh` | 判据本体；增/删/改任一测试文件都会让摘要变化 |
| `sim` | `./acceptance/soak/` | `digest-pin.sh` | 长跑与归因脚本（产出答辩证据），同样会跑在学员机器上 |
| `scripts` | `./scripts/` 整目录 | `digest-pin.sh` | **判定入口 `test-stage.sh` 在里面**：`build` 那条只锁了 `build.sh` 一个文件，判定入口被换掉时摘要必然变化 |
| `go_mod` | `./go.mod`（含 `go` / `toolchain` 行） | `digest-pin.sh` | 编译器版本是判据的一部分（race 实现、逃逸决策、分配计数都随它变） |
| `go_toolchain` | 镜像摘要 `golang:1.22.x-bookworm`（容器档位） | 人工取值后写入 `docker/go-toolchain.Dockerfile` 的 `FROM ...@sha256:`，再由 `digest-pin.sh` **回读**打印、人工核对待粘进 `track.yaml` | tag 会漂，digest 才锁得住「学员到底用哪个工具链跑判据」；同时写在 Dockerfile 与 `track.yaml` 两处，正好覆盖「构建真用它」与「脚本没被换过」两件事 |

摘要配方与 seckill 完全一致（目录递归/glob 展开 → 每文件 CRLF→LF 归一化后取 sha256 → 按相对路径 C 序排序拼 `<sha>  <path>\n` → 再取一次 sha256），**唯一改动**是把「镜像 ref 从 `docker-compose.yml` 解析」换成「从 `docker/go-toolchain.Dockerfile` 的 `FROM ...@sha256:` 行回读」——本 Track 没有 compose。

### 供应链注意

本 Track 会在学员机器上执行的东西只有四类：① **Go 工具链**（本机档位由学员自己装，容器档位由镜像摘要锁定）；② `scripts/` 三个脚本；③ 编译出来的测试二进制（源码受 `tests` / `sim` 的 pin 保护）；④ CI 配置（`.github/`，判定面内）。
**没有第三方 Go 依赖**：`scripts/verify-deps.sh` 审计 `go.mod` 无 `require` 段、`go.sum` 不存在——这条审计同时是「零依赖」这个卖点的可验证口径，也是相对 seckill（MySQL + Redis 两个镜像）更小的供应链面。但供应链面**不是零**：工具链本身就是一个巨大的依赖，这正是即便「纯进程内」也必须 pin 工具链镜像摘要的原因。

### trust_level 建议

起步 `self`（自托管、自己写的，默认信任；与 seckill-lab 一致）。升 `verified` 需要三件事同时成立：
① `contribute.review.signed_by` 有维护者背书；
② 全部入口 pin 齐（`build` / `tests` / `sim` / `scripts` / `go_mod` / `go_toolchain`），且容器档位的镜像摘要在 Dockerfile 与 `track.yaml` 两处一致；
③ **跨平台复跑判别性**：至少在 `linux/amd64` 与 `windows/amd64`（或 `darwin/arm64`）各跑一遍「base 红 / `-sol` 绿」并留日志——`-race` 的运行时实现、cgo 前置、以及 stage-06 的分配上界都随平台与工具链变，单一平台的证据不足以支撑 `verified`。

## 7. 风险、妥协与工作量

| 风险 | 影响 | 缓解 |
|---|---|---|
| **`-race` 需要 cgo + C 编译器**（Windows 上必须装 gcc，否则 `-race` 直接不可用） | 环境不合格，学员第一次跑就红在一片「-race requires cgo」，还会误以为是代码问题 | `manifest.requires` 显式声明 `race: "cgo + gcc"`；`smoke` 用 `//go:build race` 体检并给出人话错误；`docs/新手开发参考.md` 写 Windows 的 mingw-w64 安装步骤；容器档位兜底（工具链与编译器一起锁进镜像） |
| **探测器漏报**（影子内存每字 4 个槽位，理论上可能被驱逐） | 某个 stage 的骨架红不稳定 → 判别性门闪断 | 每个 stage 至少一条与 TSan 无关的锚点（§1.5 的 (a)(b)(c)(d)(e)）；`-count=3` 复跑；证据报告里对「探测器类」判据标注并给出多次运行的稳定性 |
| **无 `-race` 的假绿** | 学员直接 `go test` 拿到绿 | 判定入口 `scripts/test-stage.sh` fail-closed（编译探针 + 强制 `-race` + 用例数自检）；且本章程的结构性锚点在无探测器时**也能给出正确的红绿**，所以最坏情况是少一层保护而不是假绿 |
| **`fatal error` 终止整个测试二进制** | 报告只有「包级 FAIL」，看不出同包其它用例的结果 | 判定单位明确声明为包级；把会终止进程的场景与断言型场景分到不同测试函数；证据报告逐 stage 记录「红在哪一条断言」 |
| **分配次数/逃逸判据随工具链漂移**（stage 06） | 红绿随补丁版本变，甚至可能出现 base 假绿 | 钉 `go.mod` 的 `toolchain` 行 + `go_toolchain` 镜像摘要；上界留足余量（宁松勿假红）；标为**选修**；升 `verified` 前必须跨平台复跑 |
| **`runtime.NumGoroutine` 采样抖动**（stage 03/05） | 泄漏与上界判据 flaky | 用闸门把「在飞」变成确定的挂起态（采样取极值而非瞬时值）；结算窗口 2s（是实测回落时间的百倍量级）；naive 与正确实现差一个数量级，不靠阈值 |
| **liveness 用例挂死拖慢 CI** | 每张工单多等几秒，串起来可能几分钟 | 每个 liveness 断言显式 3s deadline；`go test -timeout=90s` 兜底；把断言型用例排在挂死型用例之前，先失败先退出 |
| **`go vet` 直接指向缺陷位置**（`lostcancel` / `copylocks`） | 难度下降，个别题可能被一句话说穿 | 接受：这是真实工具的用法，也是考点之一；把「先跑 vet 看它说什么」写成 TASKS 的观察练习；若某题被 vet 完全说穿就换缺陷形状，而不是关掉 vet |
| **作弊面**：`//go:norace`、改测试、动 `GOMAXPROCS`、把池改成全局 | 假绿 | 判定面（`acceptance/` `smoke/` `go.mod` `Makefile` `scripts/` `docker/` `.github/`）+ 入口 fail-closed；关键一点是**运行时的 map 检查不受插桩影响**（关掉插桩照样 `throw`）；D2 是君子协定，诚实记账：挡顺手，不挡铁了心 |
| **lane 正交性被后续新增代码破坏** | stage N 的红来自别的 stage 的缺陷（判别性门仍过，教学质量塌） | 把「lane 之间只共享构造期只读配置」写进 `docs/架构与约定.md`；每个 stage 的测试只 import 本 lane；证据报告逐 stage 记录「红在哪条断言」 |
| **平台准入门对 Go 的判别性跑法未知** | 门可能不带 `-race`（已缓解），或把 `smoke` 一起当输入（会让环境体检污染结果） | 列为 §8 开工前置：先确认门按 `test_group` 逐包跑；必要时给上游提一条反馈（把「Track 可声明自己的判定命令」作为契约扩展），而不是自行扩展 schema |
| **单核 / 容器限核** | stage 01 的运行时 map 检查需要真并行才触发，锚点退化 | `requires.cpu: "2"` 让体检提前提示；探测器那一层不依赖并行，所以骨架照样红；结论与限制写进证据报告 |

**工作量拆解**（人日，单人）：

- 骨架仓（6 条 lane + 组合根 + `cmd` + 文档 + `Makefile` + 4 个脚本 + 可选容器档位）**6~8**
- canonical 测试与 `testkit`（判据的真正难点：闸门/开始闸门/deadline/泄漏检测/计数/强制并行六件 + 6 组用例 + soak 4 条）**5~7**
- 题面·判据·八股地图（6 张 ticket 的正文与 `expect`/hints + 地图 + 6 份 `TASKS/stage-NN.md`）**4~6**
- 分支链 + digest pin + 判别性实测证据报告（12 次红/绿运行 + soak 证据归档）**2~3**

合计 **17~24 人日**。关键路径是 `testkit`：它定不下来，六组用例都写不实；所以实施顺序把它排在最前面。

**建议的实施顺序**

1. **`acceptance/testkit` + stage-01**。它是判据的地基，而且 stage-01 的判据最硬（运行时 map 检查不依赖探测器）——先用它证明「Go 骨架能过判别性门」这个最关键的平台假设，再写其余五关。这一步顺手实测三件规格里写死的事实：`//go:build race` 的 build tag 行为、只有 `_test.go` 的目录在 `go build ./...` 下的行为、`go.sum` 到底会不会生成。
2. **stage-02**：确定性锚点最多，用来把「活锁断言」的写法固化下来。
3. **stage-03**：泄漏检测器是 `testkit` 的第二次复用，也是「结算窗口」这条妥协的实测验证点。
4. **stage-04**：握手断言的样板，验证「把计时问题变成事件问题」这套手法可复用。
5. **stage-05**：第一次引入 soak 与 pprof，把「确定性判据 / 可观测」的边界实测划一遍。
6. **stage-06**（选修）：判据与工具链绑定，风险最高，放最后；分配上界必须按实测结果定，不能拍脑袋。
7. 分支链 + digest pin + 证据报告：照 §3 的命令序列逐阶段封板，每一级都留下红/绿日志。

## 8. 准入门自查清单

> **给 bagu-trainer 上游的两条反馈**（照 `seckill-lab/stages/README.md` 的做法，本仓不自行扩展 schema）：
> ① 准入门的「基础设施可起 / `docker compose up` healthy」一项对**无外部依赖**的 Track 应当允许 N/A——
> 本 Track 的 `runtime` 刻意不声明 `compose`，因为它的最大成本优势正是「判据全在进程内」；
> ② 判别性门的「跑 canonical 测试」目前隐含 Java/Maven 形态（`mvn -Dgroups=<test_group>`），
> 多语言需要让 Track 能声明自己的**判定命令**。本规格的过渡做法是把命令固化在判定面内的
> `scripts/test-stage.sh`，并让测试在**没有** `-race` 时仍能靠结构性锚点给出正确的红绿——
> 这样门即使按 `go test ./acceptance/<group>/...` 直接跑，判别性检查也是对的。
